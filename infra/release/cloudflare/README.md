## Client URLs

## Secret registry and mode

The runbook uses `leviathan-ai/live` entries for the deployed Worker runtime. Add the full entries from `SECRET_REGISTRY.entries.json` to `SECRET_REGISTRY.yaml`, then run `-InitializeLiveKeys` to generate all four values in process: signing private key, matching public JWK, TOTP key, and internal token. The values are written in that order, followed by `LEVIATHAN_LICENSING_LIVE_KEYSET_COMMIT`, a marker containing a keyset ID and a SHA-256 digest over the ID and all four values. Readers reject the entire set unless this marker verifies. An incomplete or stale-marker set is regenerated and replaced on retry; a valid commit is idempotent. Only explicit `-RotateLiveKeys -InitializeLiveKeys` replaces a valid committed set. Deploy checks the commit marker before any Worker operation and passes only verified values to Wrangler. The marker is registered as a secret. The fragment's `PENDING_REGISTRATION` validation status is not a successful doctor result; after registry rows are added, run the established doctor workflow and confirm no registry health errors. Live Stripe mode uses existing `STRIPE_LIVE_SECRET_KEY` and `STRIPE_LIVE_PUBLISHABLE_KEY` under `factory-admin/live`; its webhook secret has a `leviathan-ai/live` registry entry.

`STRIPE_MODE`, `STRIPE_PRICE_ID`, `LICENSE_SIGNING_KEY_ID`, `LICENSE_VERIFY_PUBLIC_KEY_JWK`, and signup URLs are non-secret Worker vars. No Hyperdrive entry/binding is used because the current runtime accepts the existing Neon `DATABASE_URL` and no Hyperdrive ID was supplied.

The deploy defaults to Stripe Test mode (`-StripeMode Test`); `-StripeMode Live` explicitly selects live keys. Test mode uses project TEST API keys. Live mode reads the owner-held `STRIPE_LIVE_SECRET_KEY` and `STRIPE_LIVE_PUBLISHABLE_KEY` from the factory-admin/live vault entries and requires `-StripeMode Live` plus a live price ID. The runbook creates or updates the Stripe webhook endpoint through the Stripe API, subscribes it to the four events below, stores the returned signing secret through `Set-XyraSecret`, and sends it to Wrangler through stdin. No dashboard action is part of the procedure. `CLOUDFLARE_MASTER_API_TOKEN` remains factory-admin/administration scoped and is only passed to the child Node/Wrangler process as `CLOUDFLARE_API_TOKEN`. `LEVIATHAN_LICENSING_DATABASE_URL` is the existing live-scoped entry. Provider API keys must be registered under the listed live project names for each provider enabled. The Worker binds Stripe `livemode` to `STRIPE_MODE` and validates API-key and Checkout-session prefixes against that same mode. Test is the runbook default; live mode cannot accept test-mode webhooks or keys.

## Coordinator runbook

1. Merge/validate the registry entries and place the Stripe test secret, test price ID, and enabled provider keys in Xyra Secrets. Confirm the existing Neon DB secret targets the intended internal-test data branch before deployment. The webhook secret is created and registered automatically during deployment.
2. Run `Deploy-LeviathanWorkers.ps1 -MasterRoot <XYRA-MASTER> -NodeExePath <pinned-node.exe> -WranglerJsPath <pinned-wrangler.js> -StripeTestPriceId <test-price-id> -WhatIf`. This plan prints binding/secret names only and performs no secret lookup.
3. Run once with `-InitializeLiveKeys` to generate the four production-isolated values. The runbook writes signing private key, matching public JWK, TOTP key and internal token, then writes the digest commit marker last. A missing/invalid marker makes the set uncommitted and retry replaces all four values; a valid marker is idempotent. Rotate a committed key set only with `-RotateLiveKeys -InitializeLiveKeys`. Deploy refuses an absent or mismatched commit marker before any Worker operation. This step requires registry rows already added and never prints key material. Run the registered SECRET_REGISTRY doctor.
4. Run the script without `-WhatIf`. It creates `leviathan-release-feed` idempotently, deploys licensing first, installs secrets by piping each SecureString to `wrangler secret put` stdin, redeploys licensing, then deploys the service-bound data gateway and release feed. Each Wrangler process receives the API token only through its child environment; process output is captured and discarded.
5. The runbook creates or updates the Stripe endpoint automatically for the selected mode. It stores the returned signing secret as `LEVIATHAN_LICENSING_STRIPE_TEST_WEBHOOK_SECRET` for Test or `LEVIATHAN_LICENSING_STRIPE_LIVE_WEBHOOK_SECRET` for Live; no Dashboard action is required. Register `https://leviathan-licensing-worker.ocean824.workers.dev/v1/signup/webhook` as the endpoint. It subscribes to `checkout.session.completed`, `invoice.paid`, `customer.subscription.updated`, and `customer.subscription.deleted`. The `whsec_...` value is written through Xyra Secrets and passed to Wrangler via stdin as `STRIPE_WEBHOOK_SECRET`. To deploy live, pass `-StripeMode Live -StripeLivePriceId <live-price-id>`; Test remains the default.
6. The script checks `/health` on each Worker, the versioned updater endpoint (204 when no newer manifest exists or 200 valid JSON), `/latest.json` (404 until that compatibility object exists, or 200 valid JSON), the licensing success/cancel routes, and the unauthenticated admin-license denial. `workers/release-feed` also serves immutable R2 objects under `/releases/{desktop|admin}/{version}/{filename}`, matching the publisher's manifest URLs.

Run the three Worker `npm test` suites, `uv run --locked python -m pytest infra/release/tests/test_update001_acceptance.py apps/admin/qa/test_admin_app_acceptance.py`, the gateway-client tests, Admin UI tests, terminal tests if its URL configuration changes, and the desktop test suite before approving the coordinator's deploy.
